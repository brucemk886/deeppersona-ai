# Paid report email delivery

The main site writes one durable `report_emails` job per confirmed paid order. `deeppersona-report-mailer` runs once a minute and processes up to 50 jobs, with a short delay between requests. Resend's account quota and rate limits still apply. The sending Worker needs its own `RESEND_API_KEY` Cloudflare secret and uses `REPORT_EMAIL_FROM` from `wrangler.mailer.jsonc`. Do not put real keys in this file or Git.

Deploy the site with the existing build/deploy workflow, and deploy the mailer separately with `wrangler deploy --config wrangler.mailer.jsonc`. Both use the existing D1 binding. Tables are created idempotently by `ensurePaymentSchema`.

The mailer skips sandbox orders, retries transient failures with backoff up to ten attempts, and stops retrying attempted messages before the provider's 24-hour idempotency retention expires. Failed jobs remain visible for manual investigation/resending. The outbox records provider acceptance, not guaranteed inbox placement or reading. The frontend unlock does not wait on Resend.

Email links carry a cryptographically random 256-bit token. D1 stores its hash for lookup and the original token for a stable retry payload. Tokens are secrets: never export them in the admin response, analytics, or support screenshots. A link grants access only to its report via an HttpOnly, Secure, SameSite=Lax cookie. It expires after 180 days; the purchase itself is not expired by this deadline. Refund status is checked independently and full refunds revoke full-report access. Users can request fresh links from `/recover`.

Recovery always returns a generic message, only emails addresses already on paid live reports, limits repeats to one job per report per five minutes, and limits each source IP to twenty requests per hour. Each request covers the ten most recent eligible reports. Older purchases can be handled through support. Email is the test-submission email, even if the payer changes the contact email at Stripe Checkout.

The dedicated admin “邮件记录” panel lists each job with search, status filters, 30-row pagination, failure counts, retry attempts, timestamps and manual resend. Resend creates a new job for only the selected paid live report, preserves the original record and enforces the five-minute cooldown. Reports with a delivered receipt display 发布成功 and cannot be resent from admin, including through older failed rows; both the API and atomic enqueue enforce this. The customer recovery flow can still send fresh access links. No raw access tokens are returned. Automated security scanners may access links: this is not proof a person read the report.

The main Worker receives signed Resend callbacks at `/api/resend/webhook` using its `RESEND_WEBHOOK_SECRET` secret. Subscribe to email.sent, email.delivered, email.delivery_delayed, email.bounced, email.complained, email.failed and email.suppressed. Svix validates the raw bounded body and timestamp. Only reports@mail.deeppersonaai.com messages are recorded; this account's other website is ignored. `report_email_delivery` stores minimal provider state separately from the send job, so callbacks arriving before the sending response are preserved. Duplicate/stale callbacks cannot regress terminal states. Provider acceptance and recipient-server delivery are distinct; delivery does not prove inbox placement or reading. Pre-webhook historical messages remain “waiting for receipt” unless explicitly backfilled from the provider's authoritative retrieval API. This view currently covers report emails, not marketing campaigns.

Verification: local integration tests use an isolated D1 database, mocked Stripe/Resend APIs, and the real mailer implementation. They cover retries, duplicate sends, recovery rate control, token scoping, expiry and refunded access. A separate authorized test message checks the verified live domain and actual provider delivery; it is not a real paid transaction.
